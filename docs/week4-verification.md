## 1. 这一周做了什么

一句话问系统,系统回答;问"采集一次"时,**真的**给板子下发任务并等回执。

```
用户输入 → nlq.py 解析意图 → app.py 执行(查内存记录 / 下发任务) → 返回答案 + 结构化数据
```

拆成两个文件是有意的:

| 文件 | 职责 | 能不能单独测 |
|------|------|------------|
| `server/nlq.py` | 只"听懂":文本 → `{intent, slots, matched, confidence}` | 能,`python nlq.py` 自测 13/13 |
| `server/app.py` 的 `/api/nlq` | 只"执行":查数据 / 下发任务 / 组织答案 | 能,起服务后 curl 或脚本 |

## 2. 设计取舍:为什么是规则式,不是大模型

| 选项 | 优点 | 为什么没选 |
|------|------|-----------|
| 调云端大模型 API | 泛化强 | 断网即废;课上有网络也不一定有 key;答案不可复现,演示会翻车 |
| 本地小模型 | 离线可跑 | 要下几百 MB 权重,环境依赖重 |
| **规则匹配(采用)** | 离线可跑、零依赖、结果可复现、**可解释** | 泛化弱 —— 用"显式展示命中关键词 + 兜底到 unknown"来兜住 |

配套的自我约束:

1. **绝不编造**:解析不出来就返回 `unknown` 并给出能做什么,不猜一个意图糊过去。
2. **可解释**:返回 `matched`(命中了哪些词),页面直接展示成小标签;判错了用户一眼看得出,而不是黑箱。
3. **动作类不谎报成功**:「采集一次」真的下发任务、真的等回执(服务端上限 12 秒)。
   板子离线时如实说"没等到回执",**不会**把"命令已下发"说成"已采集成功"。
4. **同一套代码路径**:动作类复用 `_new_task()`,与第 2 周"远程采集任务"卡片走的是同一个函数,
   所以"点按钮"和"说一句话"结果可以互相印证。

## 3. 支持的意图

| intent | 例子 | 行为 | 会下发到板子吗 |
|--------|------|------|---------------|
| `latest` | 现在加速度是多少 | 取最新一条,三轴 + 合加速度 + 距现在多久 | 否 |
| `stats` | 最近 5 分钟合加速度的最大值 | 按范围/指标/聚合统计 | 否 |
| `count` | 有多少条数据 | 条数 + 时长 | 否 |
| `device_status` | 设备还在线吗 / 信号怎么样 | 在线判定 + RSSI + 实际频率 | 否 |
| `events` | 最近有几次按键触发 | 服务端收到的事件数、未回应数 | 否 |
| `sample` | 采集一次 | **下发采集任务并等回执** | 是 |
| `pause` / `resume` | 暂停上报 / 恢复上报 | **下发命令并等回执** | 是 |
| `help` | 你能做什么 | 能力清单 | 否 |
| `unknown` / `empty` | 帮我看看天气 / 空输入 | 明说没听懂 + 给示例 | 否 |

槽位:`since_ms`(最近 5 分钟 / 过去 2 小时 / 最近一天,支持中文数字)、
`metric`(X/Y/Z/合加速度)、`agg`(最大/最小/平均/标准差/峰峰值)。

**规则顺序即优先级**:`sample/pause/resume` 放最前(否则"采集一次"会被当成查询);
`device_status` 必须排在 `stats` 前面,否则"信号怎么样"会被 stats 的泛词"怎么样"抢走 ——
这是实测中踩到并修掉的。

### 第 2 项为什么重要

`/api/nlq` 的统计和 `/api/stats` 共用同一个 `_describe_all()`,
脚本逐位比对两者数值与样本数(上面 `41.8378912094845` 完全一致)。
这样"问一句话得到的数"和"页面统计表里的数"永远对得上;
哪天有人改歪了统计口径,这里会立刻变红,而不是悄悄不一致。

### 第 3 项为什么这样设计

跑脚本时板子是离线的(最后一条数据 21 小时前)。
这时脚本**不**去验证"采集成功",而是验证**反面**:

- 状态不得是 `completed`;
- 回答里不得出现"成功"字样。

这是本周最该守住的一条:**命令已下发 ≠ 采集已完成**。

## 7. 本次发现的数据准确性问题:静止时模长只有 0.23g

**现象**:板子插电恢复上报后,合加速度稳定在 **0.23g**(应为 ≈1g),而且**非常稳定** ——
稳定到看不出有问题。对照昨晚的历史数据(平均 9.96 m/s² ≈ 1.016g),差了约 4.4 倍。

**根因**:固件启动时会做一次"重力自动校准" —— 静止时三轴模长恒等于 1g,
据此反推传感器真实灵敏度(LSB/g)。而插 USB 那一刻板子必然被晃动,
校准把这 0.9 秒里**晃动时的模长**当成了 1g,于是灵敏度被高估约 4.4 倍(约 4500 LSB/g,标称 1024),
之后所有读数都被缩小 4.4 倍。

**为什么危险**:这不是"数据抖动",而是**静默的系统性错误** —— 曲线平滑、数值稳定、
页面没有任何告警,只是整体错了 4 倍。如果直接拿去验收"静止时模长 ≈ 1g",会当场挂掉。

**修复**(`board/imu_http/imu_http.ino` 的 `qma_calibrate()`,已编译通过):

1. **静止判定**:每轮采样的相对标准差必须 < 3%,否则认为板子还在动,等 400ms 重采(最多 6 轮);
2. **取中位数**而非均值:对个别敲击尖峰鲁棒;
3. **合理区间**:结果必须落在标称值 1024 的 0.5~2 倍内,否则判定无效;
   多轮都不过则**退回标称值并打印警告** —— 宁可用标称值(偏差几十个百分点),
   也不要用一个离谱的"校准值"。

**当前状态**:三重保护已随固件烧录生效(COM5 后来枚举成功)。

### 7.1 ⚠️ 后续更正(2026-10-10):真因不是校准污染,是**数据解析错误**

上面把 0.23g 归因为"校准被晃动污染",**这个判断是错的**。校准污染确实存在、三重保护也值得保留,
但它不是 0.23g 的主因。真正的原因在 `compose14()`:

```
旧代码(错)  u = ((msb << 8) | (lsb & 0xFC)) >> 2;   // 按"左对齐"解析,多右移 2 位 = ÷4
新代码(对)  u = ((msb << 8) | lsb) & 0x3FFF;         // 右对齐:取低 14 位,按 bit13 符号扩展
```

**决定性证据**(`board/qma_diag` 量程扫描,板子静止时的 raw 模长):

| 量程档 | 实测 raw | ×4 后 | 理论 LSB/g | 换算 |
|---|---|---|---|---|
| ±2g | 1095 | 4380 | 4096 | 1.069 g |
| ±4g | 524 | 2096 | 2048 | 1.023 g |
| ±8g | 260 | 1040 | 1024 | 1.016 g |
| ±16g | 132 | 528 | 512 | 1.031 g |
| ±32g | 65 | 260 | 256 | 1.016 g |

每档都恰好差 4 倍,且 **×4 后全部 ≈1g** —— 说明量程寄存器 `0x04` 是对的,
错的只是解析。若是"校准污染"或"量程设错",不可能所有档位都同比例差 4 倍。

**修复后**:静止模长 0.95~1.02 g,中位 9.813 m/s²(偏离 1g 仅 0.1%),重力自检判合格。

**方法论教训**:校准是自洽的(它用当时的模长当 1g,所以校准完必然显示 1g),
**无法发现解析/量程这类"整体缩放"错误**。唯一可靠的外部锚点是物理常量 —— 这里用重力 1g。
发现异常时先用 `qma_diag` 扫全量程档,比猜快得多。
