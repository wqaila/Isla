## 一、项目概述

把 **ESP32-S3-EYE** 开发板(板载 QMA7981 三轴加速度计)的真实 IMU 数据,通过 WiFi 用 HTTP POST 传到本机 Flask 服务,再用浏览器实时查看与分析。同时提供 **PC 模拟器**(无传感器时联调)和**远程采集任务通道**(Web 下发命令 → 板端拉取执行 → 回执)。

### 整体架构

```
┌──────────────────┐   WiFi/HTTP    ┌──────────────────┐   HTTP    ┌─────────────┐
│  ESP32-S3-EYE    │ ─────────────▶ │  本机 Flask 服务  │ ────────▶ │  浏览器页面  │
│  QMA7981 (I²C)   │  POST /api/data│  data.json 落盘  │  GET JSON │  实时图表    │
│                  │ ◀───────────── │  tasks.json      │           │  分析/导出   │
│  命令轮询(拉取)  │  GET /api/command             │           └─────────────┘
└──────────────────┘               └──────────────────┘
        ▲                                  ▲
        │ 真实传感源(USE_QMA7981=1)         │ PC 模拟器 send_sim.py(无板子时验证链路)
```

- **上传方向**(周期):板端 20Hz 采样 → 每 200ms 聚合一次(5Hz)上传 JSON
- **命令方向**(拉取):板端每 **1s** 轮询 `GET /api/command?device_id=...`,收到任务后执行并 `POST /api/ack` 回执(端到端响应约 0.6s)

### 三端分工

| 端 | 职责 | 代码位置 |
|----|------|---------|
| 板端 | QMA7981 驱动、WiFi、周期上传、命令轮询与任务执行 | `board/imu_http/imu_http.ino`(394 行)+ `config.h` |
| 服务端 | 收数据落盘、任务队列、查询/统计/导出 API、首页 | `server/app.py`(617 行,Flask) |
| 浏览器 | 实时仪表盘、三轴/合成图、历史分析、异常检测、导出 | `server/templates/index.html` + `static/js/`(config/utils/api/charts/app) |
| 模拟器 | 无传感器时按 5Hz 发合成数据联调 | `simulator/send_sim.py` |

### 硬件与环境

- **ESP32-S3-EYE**:ESP32-S3-WROOM-1(8MB PSRAM + 8MB Flash),板载 QMA7981(地址 0x12,SDA=GPIO4/SCL=GPIO5),**免接线**
- 烧录:Micro-USB 直连(原生 USB Serial/JTAG,CDCOnBoot=cdc),优先插 USB 2.0 口
- 工具链:Arduino CLI(`C:\Program Files\Arduino CLI\arduino-cli.exe`)+ esptool;ArduinoJson 必须 6.x
- 服务端:Python venv 在 `server/.venv/`;数据落盘 `server/data.json`(JSON Lines)与 `server/tasks.json`

## 四、问题排查与修复记录(重要经验)

### 1. pause/resume 任务显示 timeout
- **现象**:板端只回 `ack(received)` 不回完成,服务器任务一直 pending → 超时。
- **修复**:① 服务端 `/api/ack` 支持 `completed` 阶段(直接置 completed 并计 elapsed);② 板端对 pause/resume 直接回 `ack(completed)`(无需上传数据)。

### 2. 服务器 count 增长慢于板端上传频率(✅ 已彻底解决)

**根因(反直觉,务必记住)**:ESP32-S3-EYE 是**原生 USB CDC**。主机**没有打开串口监视器**时,`Serial` 写入会**阻塞等待主机取数据**,把 `loop()` 卡住约 1.8 秒。

- 板端代码一直是对的(20Hz 采样 / 5Hz 上传),是被**日志打印**拖垮的。
- 现象极具误导性:**开着串口监视器时服务端收到 4.85Hz,关掉反而只剩 0.5Hz** —— 与"开着监视器会拖慢"的常识相反。

**决定性实验**:同一时间窗内做双向对比 ——
- 前台 `arduino-cli monitor` 数串口 `[UP]` 行数;
- 后台轮询 `/api/health` 的 `count` 算增速。

结果:串口侧 103 次 `[UP]`,服务端同期 4.85Hz(开着监视器)/ 0.5Hz(关掉)。一测即明。

**此前走过的弯路**(全部被证伪,留档避免重复):

| 假设 | 结论 |
|------|------|
| 板子跑的是旧固件 | ❌ 重烧后依旧 0.47Hz |
| 板端上传慢 | ❌ 串口实测 4.2Hz |
| 服务端慢 | ❌ POST 往返仅 2ms |
| 命令轮询阻塞主循环(原推测) | ❌ 调 `CMD_POLL_PERIOD_MS` 无效 |
| USB CDC 串口写入阻塞 | ✅ **成立** |

**修复**:
1. `setup()` 加 `Serial.setTxTimeoutMs(0)` —— 写不进就丢弃,绝不阻塞主循环(关键);
2. `[UP]` 日志限流到每秒 1 行(附带真实上传频率与 HTTP 耗时,保住可观测性);
3. 采样改 `while` 补帧(上限 8),HTTP 拖长时把错过的采样补回;
4. `CMD_POLL_PERIOD_MS` 2000 → 1000,远程采集响应从 **8085ms 降到 566ms**。

**效果**:0.47Hz → **4.87Hz**(10 倍),`n_samples` 1 → 4。原"建议方案"(双核心解耦 / 连接复用)**均不需要**。

### 3. 环境坑(已解决,烧录相关)
- ESP32-S3 原生 USB 需 `CDCOnBoot=cdc`;USB 3.0 口可能 Write timeout,换 USB 2.0 口;烧录后用 esptool `--after watchdog-reset` 复位,避免手动按 RST。
- 服务端重启后板端旧任务残留导致误拉取 → tasks.json 持久化 + 状态机防重复领取。

### 5.1.1 补做过程中挖出的两个数据准确性问题

**① 数据解析错误(已修,`0532d36`)**:`compose14()` 按左对齐多右移 2 位 → 所有原始值 ÷4,
静止模长只有 0.26g。用 `qma_diag` 扫全量程档定位:5 个档位都恰好差 4 倍且 ×4 后全都 ≈1g,
证明量程设置正确、只是解析错。修正后模长 0.95~1.02 g(中位 9.813 m/s²,偏离 1g 仅 0.1%)。

**② 传感器受冲击后零偏漂移(硬件限制,已记录)**:翻转/放下板子会让某轴读数锁死
(实测 Z 锁在 6.5g、Y 偏 -0.8g)。写寄存器、切 standby、软复位**都无效**,**断电 5 秒可恢复**。
应对:改变姿态用"平放旋转"代替翻转;已加**重力自检**在页面红字告警(§4)。

> 教训:校准是**自洽**的(用当时模长当 1g,校准完必然显示 1g),发现不了"整体缩放"类错误。
> 唯一可靠的外部锚点是物理常量(重力 1g)。
